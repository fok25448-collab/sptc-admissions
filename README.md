# SPTC Admissions v1.1.0

เว็บไซต์รับสมัคร วิทยาลัยเทคนิคสมุทรปราการ: เก็บโค้ดบน GitHub, รันหน้าเว็บและ API บน Vercel, เก็บข้อมูลและเอกสารส่วนตัวบน Supabase

## งานที่เพิ่มในรุ่นนี้

- แบบฟอร์มรอบโควตา (แนะแนว) ระดับ ปวช. และ ปวส. ตามเอกสารที่แนบ ปีการศึกษา 2570
- ข้อมูลส่วนตัว สัญชาติ ศาสนา วันเกิด ความพิการ เลขบัตรประชาชน โทรศัพท์ ที่อยู่แยกรายช่อง สถานศึกษา จังหวัด วุฒิ เกรดเฉลี่ย สาขาและระบบการเรียน; ปวส. เพิ่มแผนการเรียน / สาขางาน
- ปวช. ใช้วุฒิ ม.3; ปวส. ใช้วุฒิ ม.6 หรือ ปวช. เกรดเฉลี่ยขั้นต่ำตั้งใน `courses.min_gpa` (ค่าเริ่มต้น 2.00; ไฟฟ้า ปวส. 2.50)
- ระบบปกติ ทวิภาคี และสมทบ ผ่านรายการหลักสูตรจริงในฐานข้อมูล; ไม่สร้างหลักสูตรหรือจำนวนรับเพิ่มเติมเอง
- แนบรูปถ่าย JPG/PNG ≤2 MB และเอกสาร PDF/JPG/PNG รายการละ ≤5 MB: ผลการเรียน ทะเบียนบ้าน บัตรประชาชน
- เลือกยื่นออนไลน์ (แนบครบ 4 รายการ) หรือนำหลักฐานไปยื่นที่วิทยาลัย (แนบรูปถ่ายก่อน อีก 3 รายการแนบภายหลังทางเจ้าหน้าที่รับเอกสารจริง)
- หลังบันทึกสำเร็จ ดาวน์โหลด PDF ภาษาไทย A4 พร้อมรูปถ่าย เลขใบสมัคร ช่องลงลายมือชื่อ และบัตรประจำตัวผู้สมัครด้านล่างได้จริง มีฟอนต์ในไฟล์ เปิดและพิมพ์ได้โดยไม่ต้องติดตั้งฟอนต์
- ลิงก์เล็ก “สำหรับเจ้าหน้าที่ / Admin” อยู่ล่างหน้าสมัคร ผู้ได้รับสิทธิ์เข้าระบบตรวจไฟล์/เอกสารจริงและบันทึกผลได้
- ผู้สมัครกรอกเลขบัตรประชาชนและเบอร์ที่ใช้สมัครที่ `/application-status` เพื่อดูสถานะ ประวัติ ข้อความจากเจ้าหน้าที่ และสิ่งที่ต้องทำต่อ
- เก็บแบบร่างบนอุปกรณ์ 7 วันเมื่อกดบันทึก สามารถเลือกกรอกต่อหรือลบได้ ไม่บันทึกไฟล์แนบหรือ session ของ admin ลง localStorage

หน้าแรก หลักสูตร ติดต่อเรา เมนู/ท้ายหน้าร่วม และแอนิเมชันจากรุ่นก่อนยังอยู่ หน้าสมัครปรับช่องกรอกในขั้นตอน 4 ขั้นให้ตรงเอกสาร เพิ่มหน้าเช็กสถานะและหน้าเจ้าหน้าที่ โดยใช้สีและฟอนต์เดิม รองรับ reduced motion

PDF จัดทำเค้าโครงใหม่ให้อ่านและพิมพ์ได้ โดยคงข้อมูลและส่วนของเอกสารต้นฉบับ ไม่ใช่ภาพสำเนา Word แบบพิกเซลต่อพิกเซล ข้อมูลยาวอาจต่อหน้าใหม่ โดยบัตรผู้สมัครอยู่รวมกัน ไม่สร้างลายเซ็นหรือผลอนุมัติปลอม

## 1. ติดตั้ง / อัปเกรดฐานข้อมูล

ใช้ Supabase Project สำหรับเว็บไซต์นี้

**ติดตั้งใหม่:** รัน SQL Editor ตามลำดับ `supabase/001_schema.sql` → `002_courses.sql` → `003_quota_workflow.sql`

**อัปเกรดจาก v1.0.0:** สำรองฐานข้อมูลตามขั้นตอนของหน่วยงานแล้วรันเฉพาะ `003_quota_workflow.sql` จากนั้น Deploy โค้ดใหม่ รุ่นนี้ต้องใช้ migration นี้ก่อนเปิดใช้งาน หลีกเลี่ยงการส่งใบสมัครระหว่างอัปเกรด เพราะ RPC เดิมจะถูกปิดสิทธิ์

Migration เก็บใบสมัคร/เอกสารเดิมไว้ อ่านใบสมัครเดิมจากหน้า admin ได้ และไม่เปลี่ยนปีการศึกษาของฐานที่มีใบสมัครแล้ว หากจำเป็นต้องรัน SQL ทุกไฟล์ซ้ำ ให้รัน 003 เป็นไฟล์สุดท้ายเพื่อคงการปิดสิทธิ์ RPC เดิม

ตรวจว่ามีตาราง `site_settings`, `courses`, `applications`, `application_documents`, `application_reviews`, `admin_users`, `contact_messages`, `api_rate_limits` และ Storage bucket `admission-documents` เป็น **Private**

ตารางข้อมูลส่วนบุคคลและ RPC ไม่ให้ anon/authenticated เรียกโดยตรง ทุกการอ่าน/เขียนผ่าน API ที่ตรวจเงื่อนไขและสิทธิ์ก่อน โดยใช้ service-role JWT ฝั่งเซิร์ฟเวอร์

## 2. ตั้งข้อมูลการรับสมัคร

ตรวจหลักสูตรจริงใน `courses` ก่อนเปิดรับสมัคร ข้อมูลตั้งต้นมีเพียง 4 รายการที่พบในฟอร์มเก่า ไม่ได้นำหลักสูตร sample มาเปิดรับจริง

| คอลัมน์ | การตั้งค่า |
|---|---|
| `level` | ปวช. / ปวส. / ปริญญาตรี (แบบฟอร์มโควตารุ่นนี้ใช้เฉพาะ ปวช. และ ปวส.; ปริญญาตรีไปหน้าติดต่อ) |
| `system` | ระบบปกติ / ระบบทวิภาคี / ระบบสมทบ |
| `min_gpa` | เกรดขั้นต่ำ เช่น 2.00; สาขาไฟฟ้า ปวส. ตั้ง 2.50 |
| `published` | true เพื่อแสดงหลักสูตร |
| `accepting_applications` | true เพื่อเปิดรับหลักสูตรนั้น |
| `quota` | จำนวนรับต่อปี; นับทุกสถานะยกเว้น rejected/cancelled |
| `image` | URL รูปภาพ HTTPS |

Migration ปรับเกรดเฉพาะชื่อหลักสูตร ปวส. ที่ตรง “ไฟฟ้า” หรือ “เทคนิคไฟฟ้า” หากเพิ่มหลักสูตรหรือใช้ชื่ออื่น ให้ตั้ง `min_gpa` ให้ตรงเกณฑ์ของวิทยาลัยเอง

ใน `site_settings` ตรวจ `admission_year`, `quota_schedule` และตั้ง `admissions_open=true` เมื่อพร้อมรับสมัครจริง วันจากเอกสารต้นฉบับคือ:

- ประกาศผลคัดเลือก 18 ธันวาคม 2569
- รายงานตัว / ชำระเงิน 21–25 ธันวาคม 2569
- ประกาศผู้มีสิทธิมอบตัว 30 เมษายน 2570

หากวิทยาลัยเปลี่ยนกำหนด ให้แก้ `quota_schedule` ก่อนเปิดรับ ระบบเก็บสำเนากำหนดการและรายละเอียดหลักสูตร ณ วันที่สมัครในใบสมัครแต่ละใบ เจ้าหน้าที่สามารถส่งคำแนะนำใหม่ให้ใบสมัครเดิมผ่านช่อง “ขั้นตอนที่ต้องดำเนินการต่อ” ได้

## 3. สร้างผู้ดูแล

1. ใน Supabase Authentication สร้างผู้ใช้เจ้าหน้าที่ด้วยอีเมลและรหัสผ่านที่กำหนดให้เจ้าหน้าที่ พร้อมยืนยันอีเมลตามการตั้งค่าของโครงการ
2. คัดลอก User UID ของผู้ใช้นั้น แล้วรัน SQL โดยแทนค่าจริง:

```sql
insert into public.admin_users(user_id, display_name, active)
values ('USER_UUID_FROM_SUPABASE_AUTH', 'ชื่อเจ้าหน้าที่', true)
on conflict (user_id) do update set display_name=excluded.display_name, active=true;
```

3. เข้าหน้า `/admin` ด้วยบัญชีนั้น ไม่มีรหัสผ่าน admin ตั้งต้นและไม่มีหน้าสมัครสิทธิ์ admin เอง
4. ยกเลิกสิทธิ์ได้โดยตั้ง `admin_users.active=false` ระบบตรวจสิทธิ์ใหม่ทุกคำขอ

Session อยู่ใน HttpOnly cookie, SameSite=Strict, Secure บน HTTPS อายุไม่เกิน 1 ชั่วโมง จากนั้นเข้าสู่ระบบใหม่ ไม่เปิดเผย access token ใน JavaScript หรือตารางต่อเบราว์เซอร์

## 4. ตั้งค่าและรันโค้ด

ใช้ Node.js 22 ขึ้นไป:

```bash
npm ci
```

คัดลอก `.env.example` เป็น `.env.local` แล้วกรอก:

```dotenv
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVICE_ROLE_JWT
APP_SECRET=YOUR_RANDOM_SECRET_AT_LEAST_32_CHARACTERS
APP_ORIGIN=http://localhost:3000
```

คีย์ใช้ **service_role JWT จาก Legacy API Keys** ฝั่ง server เท่านั้น ไม่ใส่ในไฟล์หน้าเว็บ ไม่ commit คีย์จริง สร้าง APP_SECRET ได้ด้วย:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
npm run dev
```

เปิด `http://localhost:3000` เมื่อแก้ไฟล์ให้เริ่ม dev server ใหม่ ระบบเป็น HTML + JavaScript ที่ build เมนู/ท้ายหน้าร่วม ไม่ต้องใช้ React/Next.js

## 5. GitHub และ Vercel

อัปโหลดไฟล์โครงการทั้งหมด รวม `shared`, `api`, `server`, `src`, `public`, `scripts`, `supabase`, `tests`, `package.json`, `package-lock.json`, `vercel.json` ไป repository ของคุณ ไม่อัปโหลด `.env.local`, `node_modules`, `dist`, `test-results` หรือข้อมูลผู้สมัครจริง

Import repository ใน Vercel ใช้ Framework **Other**, Build Command `npm run build`, Output Directory `dist`, Root Directory ที่มี `package.json` ตั้ง Environment Variables ทั้ง 4 ตัว โดย `APP_ORIGIN` เป็น HTTPS origin จริง ไม่มี / ท้าย แล้ว Redeploy หากเปลี่ยนโดเมนต้องแก้ค่าและ Deploy ใหม่

ไฟล์อัปโหลดตรงเข้า private Supabase Storage ผ่าน signed URL จึงไม่ติดข้อจำกัดขนาด request ของ Vercel; API ตรวจ hash/ชนิด/ขนาดแล้วทำสำเนาที่แก้ไขไม่ได้ก่อนบันทึกฐานข้อมูล กำหนด API maxDuration 120 วินาทีใน `vercel.json`

## 6. วิธีใช้งาน

**ผู้สมัคร:** กรอก 4 ขั้น → เลือกช่องทางยื่นหลักฐาน → ยืนยันส่ง → จดเลขใบสมัครและดาวน์โหลด PDF ทันที → ลงชื่อเมื่อจะยื่นเอกสารจริง → ตรวจสถานะด้วยเลขบัตรและเบอร์เดิมได้ภายหลัง

หากเลือกยื่นด้วยตนเอง สถานะเริ่มต้นคือ “รอเอกสารเพิ่มเติม” สามารถถือใบสมัครและหลักฐานไปให้เจ้าหน้าที่ตรวจและอนุมัติในระบบเดียวกันได้ กรณีส่งออนไลน์เริ่มต้น “รับใบสมัครแล้ว” การมีเลขใบสมัครไม่ได้หมายความว่าผ่านคัดเลือกแล้ว

**เจ้าหน้าที่:** เข้าระบบ → กรองสถานะหรือค้นเลขใบสมัครเต็ม/เลขบัตรเต็ม → ตรวจใบสมัคร → เปิดไฟล์หรือรับหลักฐานจริง → ติ๊กตรวจผ่านให้ครบ → เลือกผลและใส่คำแนะนำ → บันทึก

อนุมัติ / รายงานตัวต้องตรวจผ่านหลักฐานครบ 4 รายการ รายงานตัวได้หลังอนุมัติแล้ว การขอเอกสารเพิ่ม ไม่ผ่าน หรือยกเลิกต้องมีเหตุผลให้ผู้สมัครเห็น มีประวัติการเปลี่ยนสถานะและป้องกันเจ้าหน้าที่สองคนบันทึกทับกัน หากพบข้อมูลเปลี่ยนให้กดโหลดข้อมูลล่าสุดแล้วพิจารณาใหม่

การตรวจสถานะสาธารณะเปิดเฉพาะสถานะ ชื่อที่ปิดบางส่วน หลักสูตร ประวัติข้อความและขั้นตอนถัดไป ไม่คืนที่อยู่ รูป เอกสารเต็ม หรือไฟล์ PDF เต็มผ่านเลขบัตร/โทรศัพท์ ผู้สมัครดาวน์โหลด PDF หลังส่งสำเร็จ; หากปิดหน้านั้นแล้วต้องการสำเนาอีก ติดต่อเจ้าหน้าที่ซึ่งดาวน์โหลดจากหน้า admin ได้

หากเจ้าหน้าที่ขอเอกสารเพิ่มเติมหลังส่งออนไลน์ ผู้สมัครนำไปยื่นกับงานทะเบียนได้ รุ่นนี้ยังไม่มีการอัปโหลดเอกสารทดแทนด้วยตนเองหลังบันทึกใบสมัครแล้ว

ผลล่าสุดและขอบเขตอยู่ใน `docs/VALIDATION-v1.1.md` ทดสอบกับข้อมูลสมมติ ยังต้องตรวจการอัปโหลด การล็อกอิน และวงจรสมัครจริงบน Supabase/Vercel ของเจ้าของระบบก่อนเปิดใช้งาน

ล้างไฟล์ชั่วคราวและไฟล์ที่ไม่มีใบสมัครอ้างอิงเมื่อเก่ากว่า 3 วัน:

```bash
npm run cleanup
```

คำสั่งนี้อ่านทั้งโครงสร้างไฟล์แบบเก่าและแบบใหม่ ไม่ลบเอกสารที่มีใบสมัครอ้างอิง ใช้ Storage API ไม่แก้ `storage.objects` โดยตรง รันจากเครื่องหรือ runner ที่เก็บคีย์อย่างเหมาะสม

ข้อความติดต่อยังบันทึกใน `contact_messages`; ไม่ได้ส่งอีเมลอัตโนมัติ ค่าจำกัดคำขอต่อนาทีอยู่ในแต่ละ API หากเปิดรับพร้อมกันจากเครือข่ายเดียวกันจำนวนมาก ควรปรับค่าจากผลการทดสอบโหลดจริง

ข้อจำกัดของต้นฉบับ: ไม่มี `.gs` และ `js_global.html` หรือฐานข้อมูลเดิมแนบมา ส่วน backend และการโหลดการ์ดหน้าแรกเป็นส่วนเขียนทดแทน และไม่ได้ย้ายข้อมูลผู้สมัครจากระบบเก่าที่ไม่ได้รับไฟล์มา
